# `run_local.py` H7 outer-runner audit

**Scope:** Read-only code audit against H7 in `experiments/FLUTAS_CANDIDATE5_SOURCE_RELEASE_CONTRACT_v0.3.md:360–410`. No source or test code was changed; no tests, Docker commands, builds, solvers, or GPU work were run.

## Finding

H7 remains blocked at the outer lock owner. `run_local.py` serializes GPU commands with a per-user `flock`, but on timeout or interruption it only signals and waits for the local command process group. The lock context then unconditionally unlocks. There is no container identity, Docker state query, resource sampler, or child/container termination proof in this runner. A dead Docker CLI therefore satisfies its local wait while leaving Docker Engine state unknown.

`gpu_lock_path()` selects `/tmp/fire-track2-gpu-<uid>.lock`; `gpu_lock()` takes an exclusive `flock` and always calls `LOCK_UN` in its `finally` block (`scripts/run_local.py:40–60`). In `_stop_process_group`, the first signal is followed by a one-second wait and then `SIGKILL` to the process group (`:105–133`). It waits for the direct `Popen` process, but does not enumerate surviving descendants or inspect a container. `run()` installs a SIGTERM-to-exception handler, starts the command in a new session, and waits on that client with the user timeout (`:145–158`). Timeout, SIGTERM, and Ctrl-C each call `_stop_process_group`; all then return through the `gpu_lock()` context (`:159–189`). The only final cleanup outside that context restores the SIGTERM handler (`:188–189`).

The generic resource options do not implement H7 enforcement. `--threads` sets common OMP/BLAS environment variables (`:23–31,97–103`); it does not impose a CPU quota or cgroup memory limit. `--timeout` bounds the client `wait()` and triggers the short process-group cleanup (`:82,155–166`); it is not the 1,800-second solver deadline followed by a separate, verified cleanup window. `main()` only clips the requested thread count to `effective_cpu_count()` (`:194–205`). H7 requires hard CPU/cgroup memory/wall controls plus sampled VRAM/disk stops and verified termination (`experiments/FLUTAS_CANDIDATE5_SOURCE_RELEASE_CONTRACT_v0.3.md:372–399`).

The current candidate GPU shell path is explicitly source-disabled, but illustrates the same lifecycle boundary: the locked runner starts a named `docker run --rm` and installs an EXIT/INT/TERM trap whose `docker rm -f` errors are ignored (`containers/flutas/run-candidate-gpu-regression-locked.sh:25–30,63–73`). It never queries `docker inspect` for `State.Running` or checks host children. The outer launcher invokes this script through `run_local.py --gpu --timeout 600` (`containers/flutas/run-candidate-gpu-regression.sh:74–80`). This smoke path is not a source resource profile and cannot satisfy H7.

This proves local child cleanup for that fixture, not Docker/container state or lock ordering through verification.

That module treats a successful stop/kill command result as confirmation (`scripts/run_restas_pilot.py:741–787`) and does not ask Docker for `State.Running=false`.

The fixture even writes a placeholder `scripts/run_local.py` that is never executed. Those tests validate the shell bundle path; they do not exercise the real shared lock, timeout, or signal logic.

## Smallest concrete implementation and test plan

Add an opt-in, source-specific supervised Docker lifecycle at the `run_local.py --gpu` lock owner. It must have a stable container ID before/at creation and keep the container inspectable until cleanup proof is captured; do not rely on `docker run --rm` for the supervised source run. Apply and record the frozen hard CPU and memory controls in Docker/cgroups (the current v0.3 proposal is two CPUs and 16 GiB), and enforce the solver wall deadline in the supervisor. Start monitoring before container creation; sample VRAM and the declared per-run disk roots at the v0.3 cadence, fail closed on missing/nonfinite samples or excess gaps, and dispatch a stop within the stated deadline.

Keep that host supervisor inside the lock-owning process. On timeout, threshold, sampler failure, SIGTERM, or Ctrl-C, request graceful stop with the full 10-second allowance, then force-kill the container and solver process group within one second. Verify both Docker `State.Running=false` and no surviving solver/container child within 30 seconds before the normal lock-release path. Apply the same verification after normal completion. If proof fails, do not return, raise through the current `finally`, or let an outer watchdog kill the lock holder; keep the `flock` held and escalate. Any design that lets the lock holder die must instead specify a durable quarantine that every GPU admission path checks, with its semantics independently reviewed.

Extend the CPU-only fake executable/container tests around the real `run_local.py` entry point. Use an injected clock/sleeper for deadline tests so the matrix stays short. Cover: hard CPU/memory/wall configuration; normal completion; sampled VRAM/disk threshold; sampler error, nonfinite value and overlong gap; wall timeout; SIGTERM and Ctrl-C; a graceful stop that succeeds; a child/container that ignores graceful stop and requires force-kill; Docker client exit while `State.Running=true`; a surviving solver child; inspect failure or still-running state through the 30-second verification window; lock held while cleanup is unresolved and released only after both proofs pass; and second GPU command blocked until that release. Preserve the configured limits, samples/gaps, trigger and stop timestamps, signal sequence, Docker state response, child check, and cleanup disposition in fake-run evidence. Keep the existing candidate shell offline tests as separate tests; do not treat them as runner coverage.

The Astra blocker memo already identifies the primary gap: it cites `run_local.py` timeout cleanup after about one second, unconditional GPU unlock, missing Docker state verification, and the need for the lock holder to own cleanup (`docs/reviews/BLOCKER_RESOLUTION_PLAN_ASTRA_20260925T1615Z.md:220–231`). This audit adds the exact control-flow and test-boundary evidence above: only the direct client is waited on; the generic thread limit is environment-only; the candidate offline fake bypasses the real runner; the existing pilot fake marks stop-command success as confirmation without an inspect; and the candidate shell path uses best-effort `docker rm -f` without state or child proof. Those details narrow implementation and regression coverage without changing the blocker memo's conclusion.

## Resource and gate disposition

This audit used negligible CPU for file reads. The proposed runner test matrix is CPU-only, should stay below one CPU of demand, and can remain under roughly one minute with an injected clock; no GPU is eligible or needed. H7 and source-mode execution remain blocked until the exact runner change and independent CPU fake-container review pass. This memo does not approve a launch or any prospective source limits.
